SRS-Abweichungen

Abgleich der aktuellen Implementierung mit der Spezifikation im Ordner srs/. Gefunden wurden 22 Punkte, die nicht (oder nicht vollständig) dem SRS-Standard entsprechen. Vieles davon ist bewusst oder funktional gleichwertig gelöst – die Schweregrade helfen beim Priorisieren.

A · Bewusste, dokumentierte Abweichungen

A1 Session-ID in sessionStorage statt localStorage Bewusst

SRS 1.4 (Sitzung), 8.1, 10.2, 13.9.2 – „im LocalStorage gespeichert“
Ist Die sessionId liegt in sessionStorage (lib/session.ts). Das Theme bleibt SRS-konform in localStorage.
Grund Pro-Tab-Sessions ermöglichen mehrere Spieler in einem Browser (SRS 13.9.1 „Tab = Player“). Mit localStorage würde jeder neue Tab als dieselbe Session reconnecten.

A2 Antwortfelder einspaltig statt Desktop-Tabellenlayout Bewusst

SRS 13.6.3, 14.8.1 – „Desktop: Tabellenlayout (Kategorie-Spalten)“
Ist Eingaben werden auf allen Größen untereinander gestapelt (GameScreen.tsx).
Grund Ausdrückliche Nutzer-Entscheidung (das mehrspaltige Layout wurde bewusst zurückgenommen).

A3 Zusätzliche Einstellung „Buchstaben abwählen“ Bewusst

SRS 10.9 Settings kennt nur timeLimit + showLetterDuringCountdown
Ist Settings.excludedLetters erlaubt dem Host, Buchstaben aus dem Spiel zu nehmen – eine gewollte Erweiterung über den SRS hinaus.

B · Fehlende Features aus dem SRS

B1 Host-Disconnect-Handling (30-Sekunden-Regel) Hoch

SRS 4.6, 4.8, 8.5, 11.7.1, 12.6.2, 13.4.2, 14.7.1 – HostDisconnected-Zustand, blockierender Screen, 30 s Timeout → GameOver
Ist Trennt der Host nur die Verbindung (Tab schließen), wird er lediglich als connected=false markiert. Es gibt keinen blockierenden Screen, keinen Timer und kein automatisches Spielende. Nur explizites „Verlassen“ schließt die Lobby sofort.
Wirkung Verletzt das Akzeptanzkriterium 14.7.1 (Spielende bei Host-Disconnect > 30 s). Ein hängengelassenes Spiel bleibt unbegrenzt offen.

B2 Keine automatische neue Lobby nach vollem Alphabet Mittel

SRS 9.4, 11.3.6, 11.4.3 – nach GameOver automatisch neue Lobby-Session mit neuem Code, Spieler übernommen
Ist Der Host kommt über „Zurück zur Lobby“ zurück in den Konfigurationszustand, aber mit demselben Lobbycode und ohne automatischen Ablauf. Kein neuer Code, kein Auto-Reset.

B3 Kein SyncRequired / stateVersion / acknowledgeState Niedrig

SRS 9.14.13, 9.15.2, 9.15.16, 11.7.2, 12.5.3, 12.9.2
Ist Weder Zustands-Versionierung noch ein Resync-Handshake sind umgesetzt. Konsistenz wird über vollständige State-Broadcasts + Reconnect erreicht (deckt den Zweck praktisch ab, aber ohne die spezifizierten Mechanismen).

C · Protokoll- und Format-Abweichungen

C1 Frontend validiert eingehende Nachrichten nicht mit Zod Mittel

SRS 9.3, 9.12, 13.5.3 – „Alle Nachrichten werden im Frontend mittels Zod validiert“
Ist lib/ws.ts macht nur JSON.parse und dispatcht direkt. Zod wird im Frontend nur für die Buzz-Eingabevalidierung genutzt, nicht für Server-Events.

C2 error-Payload ohne code (und severity) Mittel

SRS 9.8, 9.15.15, 12.3 – { code, message, severity } inkl. definierter Fehlercodes (INVALID_LOBBY, NOT_HOST, …)
Ist sendError sendet nur { message }. Es gibt keine maschinenlesbaren Fehlercodes und keine der in 12.3.1 definierten Codes/Severities.

C3 Server-Events ohne stateVersion Niedrig

SRS 9.15.2 – jede Server-Nachricht trägt stateVersion: number
Ist Nachrichten sind { type, payload } ohne Versionsfeld.

C4 Abweichende Feldnamen in den Payloads Niedrig

SRS 9.15.3 / 9.15.4
Ist lobbyState nutzt state statt gameState; gameState nutzt state + elapsed statt status + startedAt. Zusätzlich vorhanden: countdownRemaining, categoryCount. Funktional gleichwertig, aber nicht namensgleich.

C5 Abweichende Event-Namen für Kategorien Niedrig

SRS 9.13.8 updateCategory, 9.13.9 removeCategory
Ist Implementiert als editCategory bzw. deleteCategory.

C6 Granulare Server-Events durch konsolidiertes State-Modell ersetzt Niedrig

SRS 9.15 / 9.16 – Einzel-Events
Ist Nicht implementiert als eigene Events: playerJoined/Left/Disconnected/Reconnected, countdownStarted, roundStarted, answerState, buzzResult, scoreUpdate, liveLeaderboard, mergeUpdate, answerValidityChanged, categoryFocusChanged, reviewProgress, hostActionBroadcast, reviewLocked, finalScoreConfirmed. Stattdessen werden vollständige Zustände gesendet: lobbyState, gameState, reviewState, roundResult. Das deckt SRS 9.5 („zustandsorientierte Synchronisation“) im Geist ab.
Extra Nicht im SRS, aber implementiert: sessionCreated, buzzRejected, playerKicked, lobbyClosed, returnToLobby.

C7 Kein eigenes gameOver-Event mit reason Niedrig

SRS 9.15.14 – gameOver { finalRanking, reason }
Ist Spielende wird über roundResult mit isGameOver: true signalisiert; das reason-Feld (AlphabetFinished / HostEnded / HostDisconnected) fehlt.

C8 reconnect-Payload nutzt Top-Level-sessionId Niedrig

SRS 9.13.5 – payload: { sessionId }
Ist reconnect sendet ein leeres Payload; die sessionId kommt aus dem gemeinsamen Top-Level-Feld jeder Client-Nachricht. Funktional identisch.

D · Serverseitige Validierungslücken

D1 Buzz prüft die Buchstabenregel nicht serverseitig Mittel

SRS 5.7, 9.9 (Buzz), 9.13.15 – „alle Antworten erfüllen die formalen Regeln“ vor Rundenende
Ist handleBuzz prüft nur, dass jede Kategorie nicht leer ist (Normalize(value) != ""). Ob die Antwort mit dem aktuellen Buchstaben beginnt, prüft nur der Client (Zod). Server-Autorität ist hier unvollständig.
Abmilderung Falsche Antworten erhalten in der Bewertung ohnehin 0 Punkte; der Schaden ist gering, widerspricht aber dem „Client ist nicht vertrauenswürdig“-Prinzip (1.4 Sicherheit, 13.5).

D2 answerUpdate wird nicht auf Länge/Buchstabe validiert Niedrig

SRS 9.13.14, 9.9 (Antworten) – Länge 1–30, beginnt mit aktuellem Buchstaben
Ist Der Server speichert die Antwort ungeprüft (nur leere Werte werden verworfen). Länge wird clientseitig via maxLength begrenzt; die Gültigkeit entscheidet erst der Review.

D3 deleteCategory erzwingt kein Minimum von 1 Kategorie Niedrig

SRS 9.13.9 – „mindestens 1 Kategorie muss verbleiben“
Ist Der Host kann alle Kategorien löschen. Ein Spielstart ist dann zwar blockiert (Start verlangt ≥ 1), aber die Löschung selbst wird nicht abgewiesen.

E · Datenmodell-Abweichungen (vereinfacht)

E1 Schlankere Server-Modelle als in Kapitel 10 Niedrig

SRS 10.2–10.11
Ist Die Kernfelder sind vorhanden, mehrere Metadaten-Felder aber nicht:
  • Session: ohne createdAt, lastSeenAt, status; nutzt lobbyCode statt lobbyId.
  • Player: ohne roundScore, lastActiveAt, status; dafür Zusatzfeld left.
  • Game: ohne id, lobbyId, status, startedAt, endedAt.
  • Round: ohne gameId, endedAt, status.
  • Answer: Felder id/roundId/playerId/categoryId/…At nur implizit über Map-Schlüssel.
  • Score: ohne history-Liste.
Alle spielrelevanten Funktionen bleiben trotzdem erfüllt.

F · Infrastruktur & Projektstruktur

F1 Kein Docker und keine CI/CD-Pipeline Mittel

SRS 2.2, 2.3, 13.7, 14.12 – Docker, Docker Compose, GitLab CI/CD, automatische Images
Ist Es gibt weder Dockerfile, compose.yaml/docker/ noch eine .gitlab-ci.yml. Die Nix-Dev-Shell (flake.nix) ist vorhanden ✓, ebenso Hot-Reload (air + Vite ✓). Akzeptanzkriterium 14.12 ist damit offen.

F2 Abweichende Projektstruktur im Root Niedrig

SRS 2.3 – erwartet docker/ und compose.yaml
Ist Beide fehlen (die leere docker-compose.yml wurde entfernt). frontend/, backend/, flake.nix und README.md sind vorhanden.

G · Nicht verifizierbar / offen

G1 Performance-Ziele nicht gemessen Niedrig

SRS 13.2, 14.11 – < 80 ms Ø / < 150 ms max Roundtrip, ≥ 500 gleichzeitige Spieler
Ist Architektur (RAM, Mutex pro Hub, isolierte Lobbies) ist dafür geeignet, es existieren aber keine Last-/Latenzmessungen als Nachweis.

G2 Minimales Server-Logging Niedrig

SRS 12.9 – Logging von StateTransitions, Host-Aktionen, kritischen Fehlern, Disconnects
Ist Der Server loggt praktisch nur den Start (main.go). Zustandsübergänge und Host-Aktionen werden nicht protokolliert.

Erfüllt Konform

Diese zentralen SRS-Punkte sind sauber umgesetzt:
  • Ausschließlich WebSocket-Kommunikation (2.1, 14.2.1)
  • Server-Autorität für Punkte/Bewertung/Zustände (2.4, 13.5)

  • Punktevergabe 0/5/10/20 (7, 14.5.3)
  • Ranking mit Gleichstand + alphabetischer Sekundärsortierung (7.2)
  • 6-stelliger Zifferncode (4.3)
  • Name 1–20, Kategorie 1–30, Eindeutigkeit (4.2, 11)
  • Beitritt via Code / Link / QR (4.4)
  • Host-only-Aktionen serverseitig geprüft (10.1, 10.2)
  • Reconnect mit vollständigem State + Draft-Antworten (8, 9.10)
  • Buchstaben A–Z ohne Umlaute, keine Doppelung (5.4)
  • Normalisierung serverseitig (5.5, 9.9)
  • Buzz nur bei vollständigen Antworten (5.7)
  • Zeitlimit- und Stoppuhr-Modus (5.8)
  • Sequenzielle Verarbeitung / Idempotenz (9.6, 9.7, 11.5.3)
  • Mehrere isolierte Lobbies parallel (13.3.2)
  • Theme: System-Initial + localStorage-Persistenz (13.6.4)
  • In-Memory, keine DB (1.1, 13.11)
