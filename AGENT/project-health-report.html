Stadt Land Fluss - Code Review & Findings

Holistic scan (bugs · security · UI/UX · a11y · code quality · performance · cleanliness) · as of 2026-08-07 · branch master

Fresh full scan of the current code. All quality gates are green: backend gofmt, go vet, go test ./... incl. -race; frontend Biome, bun test (21 tests) and vite build with tsc. The server-authoritative core, end-to-end Zod validation, the connection lifecycle (host grace, reconnect with backoff+jitter, localStorage session surviving a tab close) and the hardening (origin check, rate limits/caps/join backoff, CSP/HSTS/COOP - the CSP script hash still matches the anti-FOUC snippet exactly) all hold up under re-inspection.

This pass went deeper than reading, though, and 8 findings came out of it - the previous report's "no open findings" no longer reflects the code. The most serious (GAME-1) is a scoring defect: answers from a player who left mid-game can still be counted, while the host's review screen filters them out - reproduced end-to-end, not inferred. Two medium findings are UX dead ends (a destructive action offered to players who may not perform it; a start button that silently does nothing). The rest are low-severity hygiene items across the rule mirror, concurrency, a11y and render cost. Details in section 1, the overall assessment in section 4, and the deliberate limitations (documented in the README) in section 3.

1. Open findings

Sorted most severe first. Every finding names the exact place and was checked against the running code, not against an earlier report.

high A departed player's answers still count towards scoring GAME-1

backend/internal/websocket/game_handlers.go:483 (scoreAndFinishRound) · backend/internal/websocket/handlers.go:387 (handleLeaveLobby) · backend/internal/websocket/handlers.go:308 (handleReconnect)

Three gaps line up into one scoring defect. First, a mid-game leaveLobby marks the player Left and drops them from hub.clients, but - unlike the pre-game branch two lines above and unlike handleKickPlayer - it does not delete hub.sessions[sessionID]. The session stays valid. Second, handleReconnect has no Left guard: it happily sets player.Connected = true again, and isRoundSpectator (which gates answerUpdate/inputSync) does not consider Left either - so the returning player can write answers into the live round. Third, and this is the part that bites, scoreAndFinishRound filters only on isRoundSpectator, while buildReviewState (game_util.go:239) and hasActiveSubmission (game_util.go:108) do filter pl.Left. The review screen and the scoring therefore disagree about who is in the round.

Reproduced end-to-end against the real WebSocket handler: after Bob leaves mid-round and reconnects with his old sessionId, his injected answer never appears in the host's review (1 answer shown, the host's own) but is scored - the host drops from the expected 60 to 45 points because his unique answer is silently demoted to a shared one, and Bob is credited 5 points despite having left. The host cannot see or invalidate the answer that changed the result.

Not reachable from the stock frontend, which clears the stored sessionId on an explicit leave - it takes a client that kept the id. But the whole architecture rests on the server not trusting the client, and a future frontend change could open the path by accident.

Recommendation: fix all three layers. Delete the session on a mid-game leave (mirroring handleKickPlayer); reject a reconnect for a player with Left == true; and add the pl.Left filter to scoreAndFinishRound so its view of the round matches buildReviewState. A regression test in integration_test.go along the reproduction above is cheap - the harness already has everything it needs.

medium Non-hosts are offered the "remove player" action in the standings UX-1

frontend/src/pages/game/RoundResultScreen.tsx:129-138

In the between-rounds standings each player's name is a button that opens the "X entfernen?" confirmation. The condition is only r.playerId !== myPlayerId && !hasLeft(r.playerId) - there is no isHost gate, even though the component computes isHost and uses it a few lines below for the button bar. So every ordinary player sees other names render as clickable (hover:line-through cursor-pointer), can open the destructive dialog, confirm it, and is then answered by the server with NOT_HOST → a "Aktion nicht erlaubt" error toast. The lobby's player list (Lobby.tsx:449) gets this right with isHost && !leaving && ….

Secondary point, this time for the host too: the destructive trigger is an otherwise unlabelled player name whose only affordance is a hover strikethrough. There is no icon, no accessible description of what activating it does.

Recommendation: gate the button on isHost, and give the host the same explicit control the lobby list uses (an X icon button with a title) instead of overloading the name.

medium "Spiel starten" silently does nothing when no participant is connected UX-2

frontend/src/pages/Lobby.tsx:326-329 · backend/internal/websocket/game_handlers.go:34-46 · backend/internal/websocket/game_handlers.go:78

Both the client's canStart and the server's commentator check count players without looking at connected: the client filters activePlayers on !p.left only, the server counts every non-host player in lobby.Players. But beginCountdown then applies the stricter hasRoundParticipant (connected, not left, and not a commentator host), finds nobody, resets lobby.Game = nil, falls back to StateLobby and broadcasts an unchanged lobby.

Concretely: commentator mode is on and the one co-player closes their tab. Their row still shows in the list (greyed dot), the start button stays enabled, the host clicks it - and nothing at all happens. No round, no error, no explanation. The state machine shortcut itself is deliberate and documented; the missing feedback is not.

Recommendation: count only connected players in canStart and in the server's start check (so the button disables with its existing hint text), and/or have the beginCountdown fallback send an explanatory error to the host instead of returning silently.

low The client rule mirror diverges from the engine on non-ASCII input RULE-1

frontend/src/lib/answerValidation.ts:11,22 vs. backend/internal/game/engine.go:59,72

CLAUDE.md declares the mirror an explicit invariant ("keep both in sync … the tests cover this"). Two JS-vs-Go semantics differences break it:

  • Length. The mirror checks n.length - UTF-16 code units - while the engine counts runes. Interestingly normalize already uses [...v] for the first character, so the file is inconsistent with itself.
  • Case mapping. JS toUpperCase() applies Unicode special casing (ß → SS); Go's per-rune strings.ToUpper leaves ß alone.

Both verified by running the two implementations side by side. "ßeta" on letter S: the mirror normalises to "SSeta" and calls it valid, the engine keeps "ßeta" and calls it invalid - the buzz button lights up and the server answers buzzRejected: invalidAnswers, a dead end with no explanation. In the other direction "A" + 15 emoji is 16 runes (engine: valid) but .length 31 (mirror: invalid), so a field is marked red that the server would have accepted.

Recommendation: count [...n].length and make the first-rune uppercase rune-safe (or compare the leading rune case-insensitively instead of upper-casing the whole string). Add the two cases above to answerValidation.test.ts - the current suite has no non-ASCII length or casing case, which is why the drift went unnoticed.

low Client.sessionID is written from foreign goroutines without synchronisation CONC-1

backend/internal/websocket/hub.go:337 (closeLobby) · backend/internal/websocket/handlers.go:667 (handleKickPlayer) · read in lookupLocked, written in registerSession (hub.go:161) and handleReconnect (handlers.go:347)

Both closeLobby and handleKickPlayer assign c.sessionID = "" on other clients after releasing h.mu. Each victim's own read loop meanwhile reads that same field under h.mu (every handler starts with lookupLocked(c.sessionID)) and writes it in registerSession/handleReconnect. No single lock covers both sides, so the field is formally unsynchronised; a torn read of the string header (pointer from one value, length from another) would take the whole process down, not just one lobby.

Honest caveat: go test -race does not currently flag it. Probes were written for both the kick and the close path and run under -race up to ten times without a report - the websocket write that immediately follows each assignment happens to establish the ordering. That is incidental library behaviour, not a guarantee, which is why this is reported as latent rather than observed.

Recommendation: move the assignment inside the h.mu section that already collects the targets, so the field is covered by the same lock its readers use. A comment noting that sessionID is hub-mutex-guarded would keep the next change honest.

low Inline form errors are neither associated nor announced A11Y-1

frontend/src/pages/Home.tsx:471-473, 542-544 · frontend/src/components/ConfirmDialog.tsx:71-110

The code and join-name inputs correctly set aria-invalid, but the error paragraph beneath them has no id and the input no aria-describedby, and the paragraph carries neither role="alert" nor aria-live. A screen-reader user is told the field is invalid but never why - and "Diese Lobby gibt es nicht." is exactly the information they need.

In the same area: ConfirmDialog traps Tab and focuses the confirm button on open (both good), but does not restore focus to the element that opened it on close, so a keyboard user is dropped back to <body> after every kick/delete/leave dialog.

Recommendation: give the error paragraph an id, point aria-describedby at it while it is shown, and add role="alert". In the dialog, capture document.activeElement on mount and refocus it in the cleanup.

low Positive tabIndex overrides the document tab order A11Y-2

frontend/src/pages/game/GameScreen.tsx:451, 464

With flames enabled the answer inputs get tabIndex={idx + 1} and the flame buttons tabIndex={categories.length + idx + 1}, to make Tab walk all inputs before all flames. The side effect is bigger than the intent: any positive tabindex jumps ahead of every tabindex="0" element in the document, so the header's copy-code and "Verlassen" buttons, the theme toggle and "Runde beenden" are all pushed behind the category grid - and the tab order changes structurally depending on whether flames are on.

Recommendation: achieve the grouping through DOM order (render the inputs and the flame buttons as two passes / two columns) and keep every control at the natural tabindex="0".

low A fresh Zod schema is built on every validation call PERF-1

frontend/src/lib/answerValidation.ts:17 (answerSchema), called from GameScreen.tsx:325, 416 and validateAnswers

answerSchema(letter, lastLetter) constructs a new z.string().transform().refine().refine() chain on every invocation, and the render path calls it about 2n + 1 times per render (once per category for isAnswerDone, once for showInvalid, plus validateAnswers) - on every keystroke, since the answer state lives in the component. The letter and mode are constant for a whole round, so all of that construction is repeated work.

Small in absolute terms at party-game category counts, which is why this is low - it is listed as avoidable per-keystroke work, not as a measured problem. The existing performance report does not cover it.

Recommendation: memoise the schema by (letter, lastLetter) in a module-level cache, or drop Zod on this path entirely - the two rules are a length check and a prefix/suffix check, both one-liners.

2. What is already strong

  • plus Connection lifecycle: host grace with a stable deadline ticker (no more second-by-second jump-back), a snapshot-carried countdown, a clean 1001 shutdown and reconnect with backoff+jitter, incl. an expiry test (-race green). The session lives in localStorage and survives closing the tab: re-entry as the same player (the host keeps its role within the grace window), an explicit "leave" is final.
  • plus Join anytime: you can join a running lobby in any phase. Mid-game joiners are Pending on the server, spectators with a fill-in overview, cleanly excluded from scoring/ranking/review/buzz (isRoundSpectator), and are activated automatically at the next round start. Covered by integration tests (pending status + activation).
  • plus Accessibility basics: a <main> landmark, live regions deliberately decoupled from the second ticker (the host-grace banner announces the situation once and hides the ticking digits), a focus trap plus Escape in the modal, aria-pressed on the letter and flame toggles, keyboard operation throughout, toasts that pause on hover/focus. Two gaps found this round - unannounced field errors and positive tabindex - are A11Y-1/A11Y-2.
  • plus Frontend robustness: an ErrorBoundary (also around lazy chunks), a stackable 3D toast system with error/info variants, a join pre-check (checkLobby) with navigation locked during the check.
  • plus Tests: Go WS integration tests at the protocol level (-race green, ~15 s) and a frontend suite on the native bun test runner (21 tests) covering the client mirror of the engine rules (answerValidation) and parseServerEvent (Zod). Both run in CI. The Go harness in particular is good enough that reproducing GAME-1 end-to-end took a single test function on the existing helpers.
  • plus Server-authoritative & end-to-end Zod validation of all incoming events (incl. host and checkLobby events).
  • plus Hardening: origin check, rate limit + caps + join backoff (also for the pre-check), a lobby reaper, CSP/HSTS-preload/COOP, immutable asset caching, hashed session IDs, no sessionId leak.
  • plus Render efficiency: all store accesses use fine-grained Zustand selectors (useStore(s => s.field)) instead of subscribing to the whole store, so components re-render only for the fields they read. Room hangs only on lobby?.state, for example, so the route tree no longer re-renders on every hostGrace second tick. Timer screens deliberately tick on local state, not on the store.
  • plus Consistency & CI: uniform sort idioms, TypeScript strict, Biome clean, a gofmt gate, bun test + WS integration tests in the pipeline, and a Nix flake that pins the whole toolchain.
  • plus Commentary that earns its keep: nearly every non-obvious decision carries its rationale (why the write happens after the unlock, why EmptySince is owned solely by the janitor, why the clipboard fallback exists). That is what made this scan able to separate deliberate choices from oversights - several things that look wrong at first glance turned out to be documented and correct.

3. Deliberately decided (no action needed)

The following points are chosen deliberately and documented in the README under "Deliberate decisions & known limitations". Each was re-checked against the code this round and still holds. They are not a problem for the intended use (LAN/party game) and are listed here so they are not re-raised as findings.

  • No host handoff: if the host does not return within 15 s, the lobby is closed, deliberately not transferring the host role.
  • Host "end round" is a fallback: a round normally ends through the first buzz or the timeout. The host button "end round" is deliberately de-emphasized (ghost) and only meant for the special case that no one can find anything else, it is not a standard flow.
  • A single global hub.mu: serializes all lobbies; at 500 players avg < 5 ms. Sharding is only needed with very many parallel games.
  • execCommand clipboard fallback: for plain-HTTP LAN, where navigator.clipboard is missing, deprecated but widely supported.
  • Player-list cache: evaluated and rejected, almost every broadcast follows a connected/score change that would invalidate a cache anyway.
  • No persistence layer: state lives in RAM; after a server restart clients are disconnected cleanly and return to the home screen.

4. Final project analysis

Overall verdict: still shippable for the intended use (real-time multiplayer party game on the LAN/browser), with one scoring defect worth fixing before the next session. The architecture, hardening and test discipline are genuinely good and hold up under scrutiny. What changed relative to the previous report is not the code but the depth of the check: probing the leave/reconnect path against the real handler surfaced GAME-1, and walking the screens as a non-host surfaced UX-1. Neither was visible from reading the happy path.

Architecture & code quality

Clear separation: the Go backend as the single source of truth (engine, state machine, hub/handlers separated), the React SPA as a pure view layer. The state machine per lobby (Lobby -> Countdown -> Playing -> Reviewing -> RoundResult -> GameOver) is cleanly encapsulated; timers are idempotent via roundID+state, so late callbacks on aborted rounds fizzle out without effect. The code is commented throughout (every non-obvious decision with a rationale) and stylistically homogeneous.

The one structural weakness this pass exposes is that "who is in the round" is decided in four separate places - isRoundSpectator, hasRoundParticipant, hasActiveSubmission and the inline filters in buildReviewState/scoreAndFinishRound - each with a slightly different notion of Left and Connected. GAME-1 is exactly the seam between two of them, and UX-2 is the seam between two others. Consolidating that into one predicate (or a small set of named, documented ones) would remove a whole class of future findings.

Concurrency

A single global hub.mu serializes all lobby state; writes to the sockets happen after unlocking (coder/websocket serializes Conn.Write internally). Reconnect races are defused via identity guards (only the currently bound connection cleans up). go test ./... -race is green, incl. the end-to-end WebSocket tests. The one exception to the discipline is Client.sessionID, which is assigned across goroutines outside the mutex (CONC-1) - latent rather than observed, but it is the only field in the package that escapes the lock.

Tests & CI

Backend: engine unit tests, benchmarks and protocol-level WS integration tests (among others a full round cycle, host-grace expiry, mid-game join -> pending -> activation). Frontend: the Zod parser and the engine-rule mirror, now on the native bun test runner - which also retired the zod-inlining workaround vite.config.ts needed under Vitest, so the build config is test-free again.

Gaps. There are no render tests for the React components/screens; the UI is guarded only by typecheck, lint and manual variant runs - which is precisely why UX-1 (a missing isHost gate) survived. And the mirror suite that is supposed to enforce the engine-rule invariant contains no non-ASCII case, which is why RULE-1 went unnoticed. Both suggest the same thing: the tests cover the paths that were thought through, not the edges.

Security

Server-authoritative with end-to-end input validation; a WS origin check against CSWSH (IP parsing instead of a glob), a per-connection rate limit, resource caps, a join backoff against code enumeration, an abandoned-lobby reaper. A strict CSP (script hash instead of unsafe-inline), HSTS/COOP/nosniff, hashed session IDs in logs, no sessionId leak to other clients. The CSP script hash was recomputed from index.html this round and still matches the value in main.go exactly. Appropriate for a game without accounts/persistence and without personal data.

The one place where the server does not live up to its own "never trust the client" rule is session invalidation on a mid-game leave (GAME-1): it relies on the frontend clearing localStorage rather than dropping the session itself. The kick path next to it does it correctly, so this reads as an oversight, not a policy.

UX & a11y

The host role is guided very well: inline field errors, confirmations on every destructive action, connection feedback, the commentator beamer view, QR/deep-link joining, "join anytime", and a start button that deliberately stays focusable while disabled so a click can shake the explanatory hint. The join flow is unusually careful - it seeds browser history so the back gesture walks the steps, pre-checks lobby availability before asking for a name, and discards stale replies.

Walking the flows as a non-host is where it thins out. The round-result screen offers an action that only the host may perform (UX-1), and the one genuine dead end found this round - clicking start with nobody connected (UX-2) - produces no feedback whatsoever. A11y is solid on structure (landmark, focus trap, deliberate live-region design, aria-pressed toggles) but has two concrete gaps in A11Y-1/A11Y-2. Responsive, light/dark theme, and animations fully disabled under prefers-reduced-motion.

Suggested order of work

If the findings are picked up, this order gets the most out of the least effort:

  • 1. GAME-1 - the only finding that changes game outcomes. Fix the three layers together and pin it with a regression test; the reproduction is already written out in section 1.
  • 2. UX-1 and UX-2 - both are small, visible to every player, and independent of each other.
  • 3. The consolidation described under "Architecture": one documented predicate for round participation. Doing it right after GAME-1/UX-2 means fixing the seam rather than patching both sides of it.
  • 4. The remaining low findings - RULE-1, CONC-1, A11Y-1, A11Y-2, PERF-1 - in any order; each is self-contained and none blocks play.

Beyond the findings, two standing ideas: lightweight render/interaction tests for the core screens (which would have caught UX-1), and an optional persistence layer if lobbies should ever survive a server restart - currently in-memory by design.

This report only documents, it reflects the current state without history. Nothing here blocks playing the game today; GAME-1 is the one finding worth resolving before it is used competitively, since it can silently change who wins.
