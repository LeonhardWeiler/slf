1. Open findings

Currently no open findings. All gates (gofmt, go vet, go test incl. -race, Biome, Vitest, vite build) are green.

2. What is already strong

  • plus Connection lifecycle: host grace with a stable deadline ticker (no more second-by-second jump-back), a snapshot-carried countdown, a clean 1001 shutdown and reconnect with backoff+jitter, incl. an expiry test (-race green). The session lives in localStorage and survives closing the tab: re-entry as the same player (the host keeps its role within the grace window), an explicit "leave" is final.
  • plus Join anytime: you can join a running lobby in any phase. Mid-game joiners are Pending on the server, spectators with a fill-in overview, cleanly excluded from scoring/ranking/review/buzz (isRoundSpectator), and are activated automatically at the next round start. Covered by integration tests (pending status + activation).
  • plus Accessibility: a <main> landmark, a live region decoupled from the second ticker, labels, aria-live/aria-invalid, keyboard operation, pausable toasts, an AA-capable contrast token.
  • plus Frontend robustness: an ErrorBoundary (also around lazy chunks), a stackable 3D toast system with error/info variants, a join pre-check (checkLobby) with navigation locked during the check.
  • plus Tests: Go WS integration tests (-race) and a new frontend Vitest setup, the client mirror of the engine rules (answerValidation) and parseServerEvent (Zod) are covered, both run in CI.
  • plus Server-authoritative & end-to-end Zod validation of all incoming events (incl. host and checkLobby events).
  • plus Hardening: origin check, rate limit + caps + join backoff (also for the pre-check), a lobby reaper, CSP/HSTS-preload/COOP, immutable asset caching, hashed session IDs, no sessionId leak.
  • plus Render efficiency: all store accesses use fine-grained Zustand selectors (useStore(s => s.field)) instead of subscribing to the whole store, so components re-render only for the fields they read. Room hangs only on lobby?.state, for example, so the route tree no longer re-renders on every hostGrace second tick. Timer screens deliberately tick on local state, not on the store.
  • plus Consistency & CI: uniform sort idioms, TypeScript strict, Biome clean, a gofmt gate, Vitest + WS integration tests in the pipeline.

3. Deliberately decided (no action needed)

The following points, raised in earlier rounds, are chosen deliberately and documented in the README under "Deliberate decisions & known limitations". They are not a problem for the intended use (LAN/party game) and are listed here only for completeness.

  • No host handoff: if the host does not return within 15 s, the lobby is closed, deliberately not transferring the host role.
  • Host "end round" is a fallback: a round normally ends through the first buzz or the timeout. The host button "end round" is deliberately de-emphasized (ghost) and only meant for the special case that no one can find anything else, it is not a standard flow.
  • A single global hub.mu: serializes all lobbies; at 500 players avg < 5 ms. Sharding is only needed with very many parallel games.
  • execCommand clipboard fallback: for plain-HTTP LAN, where navigator.clipboard is missing, deprecated but widely supported.
  • Player-list cache: evaluated and rejected, almost every broadcast follows a connected/score change that would invalidate a cache anyway.
  • No persistence layer: state lives in RAM; after a server restart clients are disconnected cleanly and return to the home screen.

4. Final project analysis

Overall verdict: production-ready for the intended use (real-time multiplayer party game on the LAN/browser). Over several review rounds the project has matured into a consistent, well-tested and deliberately hardened state. There are no known correctness, security or a11y defects; the remaining limitations are all deliberate, documented design decisions (section 3).

Architecture & code quality

Clear separation: the Go backend as the single source of truth (engine, state machine, hub/handlers separated), the React SPA as a pure view layer. The state machine per lobby (Lobby -> Countdown -> Playing -> Reviewing -> RoundResult -> GameOver) is cleanly encapsulated; timers are idempotent via roundID+state, so late callbacks on aborted rounds fizzle out without effect. The client-side answer validation mirrors the engine rules and is guarded against drift by Vitest. The code is commented throughout (every non-obvious decision with a rationale) and stylistically homogeneous.

Concurrency

A single global hub.mu serializes all lobby state; writes to the sockets happen after unlocking (coder/websocket serializes Conn.Write internally). Reconnect races are defused via identity guards (only the currently bound connection cleans up). go test -race is green, incl. the end-to-end WebSocket tests.

Tests & CI

Backend: engine unit tests, benchmarks and protocol-level WS integration tests (among others a full round cycle, host-grace expiry, mid-game join -> pending -> activation). Frontend: the Zod parser and the engine-rule mirror. The GitLab CI runs on oven/bun without Node; the Bun runtime quirk (zod inlined in vite.config.ts) is deliberately solved and documented. Gap (not critical): there are no render tests for the React components/screens, the UI is guarded via typecheck, lint and manual variant runs.

Security

Server-authoritative with end-to-end input validation; a WS origin check against CSWSH (IP parsing instead of a glob), a per-connection rate limit, resource caps, a join backoff against code enumeration, an abandoned-lobby reaper. A strict CSP (script hash instead of unsafe-inline), HSTS/COOP/nosniff, hashed session IDs in logs, no sessionId leak to other clients. Appropriate for a game without accounts/persistence and without personal data.

UX & a11y

Both roles are guided throughout (inline field errors, confirmations for destructive actions, connection feedback, the commentator beamer view, QR/deep-link joining, "join anytime"). A11y: a <main> landmark, a focus trap in the modal, variant-dependent live regions, keyboard operation, pausable toasts, AA contrast. Responsive and with a light/dark theme.

Optional next steps (non-blocking)

Only ideas in case the project is picked up again later, none of it is needed for a close-out:

  • Lightweight render/interaction tests for the core screens (e.g. Testing Library) as a complement to the existing logic tests.
  • An optional persistence layer (e.g. Redis) if lobbies should ever survive a server restart, currently deliberately purely in-memory.

This report only documents, it reflects the current state without history. None of it is blocking; the app is in a good, shippable state and can be closed out as is.
