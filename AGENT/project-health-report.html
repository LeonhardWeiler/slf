Stadt Land Fluss - Code Review & Findings

Holistic scan (bugs · security · UI/UX · a11y · code quality · performance · cleanliness) · as of 2026-08-07 · branch master

Fresh full scan, with the central flows walked on a running server. The declared gates are green: backend gofmt, go vet, go test ./... incl. -race; frontend Biome lint, bun test (26 tests) and vite build with tsc. A live protocol walkthrough (create → join → start → buzz → review → result → next round → game over → return to lobby → host leaves, plus mid-game join, kick, leave and replayed sessions) behaved exactly as documented in every step but one - see UX-1.

The core is unchanged and still strong: server-authoritative rules, the one documented predicate set for round participation, end-to-end Zod validation, the connection lifecycle and the CSP script hash (recomputed from index.html this round, still matching main.go exactly). What this pass turned up instead sits at the edges: the one resource path that is not throttled, a modal that never got the focus handling its sibling has, a name that stays reserved by the player who left, and a format gate that exists for Go but not for TypeScript. 10 open findings, none critical or high. The overall assessment is in section 4; deliberate limitations (documented in the README) are in section 3.

1. Open findings

Sorted from most to least urgent. Nothing here is critical or high: the game plays correctly end to end, and none of these can change a game's outcome.

medium Lobby creation is the only unthrottled resource path SEC-1

backend/internal/websocket/handlers.go - handleCreateLobby; cf. client.go (joinBackoff) and hub.go (maxLobbies)

Every other resource path is guarded: joins have a growing backoff after 5 failures, messages a per-connection token bucket (40/s), players and categories hard caps. createLobby has nothing of the sort - only the global maxLobbies = 10000. Measured against the running server: a single socket created 300 lobbies in 8.5 s with zero pushback (self-throttled to stay under the message limit; the token bucket is the only ceiling). At the full message rate the global cap is reachable in roughly four minutes from one connection, and from then on every legitimate createLobby is refused with "Server ausgelastet". It does heal itself - the janitor reaps lobbies with no connected player - but only after EmptySince is set on a 2-minute pass plus the 10-minute TTL, so the denial window is ~12 minutes per wave.

Only reachable by whoever can open a WebSocket, so on a closed LAN this is theoretical. It matters for the public-deployment shape the project already supports (Docker image, HSTS with preload, WS_ALLOWED_ORIGINS for a real domain).

Recommendation: give creation the same treatment joining already has - a per-connection quota or growing backoff (c.createdLobbies alongside c.joinFails), so one client cannot walk the global cap on its own.

medium The QR modal is aria-modal without any of the focus handling A11Y-1

frontend/src/pages/Lobby.tsx (QR popup) - compare frontend/src/components/ConfirmDialog.tsx

The "QR anzeigen" popup declares role="dialog" aria-modal="true" and does lock body scroll and close on Escape/backdrop - but unlike ConfirmDialog it never moves focus into the dialog, never traps Tab inside it, and never returns focus to the trigger on close. A keyboard or screen-reader user opening the QR code keeps focus on the button behind a surface that claims to be modal, tabs straight into the visually obscured page, and after closing is left wherever they ended up. ConfirmDialog solves all three in ~20 lines it already has; the QR dialog simply never got them.

Recommendation: reuse the pattern from ConfirmDialog (focus the close button on open, cycle Tab within the panel, restore document.activeElement on unmount) - or lift that dialog chrome into one shared component so a third modal cannot repeat this.

medium Leaving mid-game keeps your own name reserved against you UX-1

backend/internal/websocket/handlers.go - handleJoinLobby (name-uniqueness loop); game_handlers.go - resetForNewGame

The uniqueness check scans all lobby.Players, including players marked Left - and those are only dropped at the next resetForNewGame (a new game or a return to the lobby). Verified live: after "Verlassen" mid-game, rejoining the same lobby as the same person is rejected with NAME_NOT_UNIQUE / "Name bereits vergeben". The same applies after a kick.

The failure is opaque from the player's side: the join screen shows no player list, and in the lobby their row is already gone (players.filter(p => !p.left)), so the name they can see nobody using is refused with no explanation. Their only way back in is to invent a different name - and then they sit in the standings twice, once as their departed self. For a party game where a mistaken tap on "Verlassen" is the most likely way to leave, this is the roughest edge the walkthrough found.

Recommendation: exclude Left players from the uniqueness check (the departed row keeps its name in the standings, which is what it is there for), or - if a clash must stay impossible - say so: "Dieser Name gehört noch zu einem Spieler, der das Spiel verlassen hat."

low Biome's formatter is enabled but never enforced - and the tree has drifted CI-1

frontend/package.json (lint script), frontend/biome.json, .gitlab-ci.yml

biome.json enables the formatter, but nothing ever checks it: bun run lint is biome lint src - lint only, src only - and CI runs exactly that script. biome format . currently reports 8 unformatted files, four of them under src/: answerValidation.ts, serverEvents.ts, Lobby.tsx and index.css - i.e. files touched in the last fix pass and never reformatted. The remaining four are biome.json itself, package.json, tsconfig.json and vite.config.ts.

The asymmetry is the actual point: the backend has a hard gofmt gate that fails the pipeline on a single stray file, while the frontend has no counterpart at all - so formatting drift is invisible until someone runs the formatter by hand.

Recommendation: switch the script to biome check . (lint + format, whole project) or add a biome format --check . step next to it in CI, then run the formatter once to clear the current drift.

low Live regions that appear together with their content A11Y-2

frontend/src/components/Toaster.tsx, ConnectionBadge.tsx, QrScanner.tsx

Toaster returns null while the queue is empty, so its aria-live container enters the DOM at the same moment as the first toast. Screen readers generally announce changes inside an already-present live region; a region inserted together with its text is commonly missed. The same shape applies to ConnectionBadge (role="status", rendered only while disconnected), so "Verbindung getrennt" can pass silently. The QR scanner's camera error is a plain <p> with no live semantics at all.

HostGraceBanner is not affected: it uses role="alert", which is announced on insertion - the deliberate split between the static alert text and the aria-hidden ticking digits still works as designed.

Recommendation: always render the live-region wrapper (empty) and only swap its children - for the toaster, move the aria-live div above the toasts.length === 0 early return. Give the scanner error role="alert".

low A briefly disconnected player is announced as having left UX-2

frontend/src/pages/game/RoundResultScreen.tsx and GameOverScreen.tsx - hasLeft()

hasLeft(id) is p.left || !p.connected, so a three-second connection drop labels that player "(verlassen)" in the standings for everyone - while the lobby list shows the very same player with a neutral pulsing "reconnecting" dot. Two screens tell different stories about one state, and the wrong one is the more public.

The same predicate also gates the host's kick affordance in the standings, so a player who drops out for a moment silently becomes unremovable - the one moment a host is most likely to want to remove them.

Recommendation: render the two states distinctly - "(verlassen)" only for p.left, and something reversible (greyed name, the lobby's pulsing dot) for !p.connected - and gate the kick action on p.left alone.

low The round-start precondition is checked in a different critical section than the transition CONC-1

backend/internal/websocket/game_handlers.go - handleStartGame, handleStartNextRound, beginCountdown

beginCountdown performs its whole mutation under one lock, but its callers verify the precondition (State == Lobby/GameOver, resp. State == RoundResult) in an earlier critical section and release the lock before calling it. Between the two, nothing holds: beginCountdown re-checks only lobby.Game != nil, whereas its siblings beginPlaying and endRound deliberately re-verify roundID and state.

Two live sockets on one session can therefore both pass the check and start two rounds, silently consuming an extra letter. That is not exotic by design: all tabs of a browser share one sessionId (documented), and a connection replaced by handleReconnect stays usable until its socket actually closes - lookupLocked never checks that the caller is still the client bound to the session.

Not reproduced: eight attempts with two sockets firing startGame simultaneously consumed exactly one letter every time. This is a hardening item about a structural gap, not an observed defect - which is why it sits at low.

Recommendation: pass the expected state into beginCountdown and re-check it under the same lock that performs the transition (mirroring the roundID+state guard in beginPlaying). Optionally have lookupLocked also assert hub.clients[sessionID] == c, so a superseded socket stops acting for the session.

low No render tests for the React screens TEST-1

frontend/src/ - only answerValidation.test.ts and serverEvents.test.ts exist

The logic layer is well covered (26 frontend tests, plus protocol-level Go integration tests), but no test ever renders a component. Everything that lives in JSX - conditional host affordances, disabled states, focus behaviour, which screen a phase maps to - is guarded only by typecheck, lint and manual runs. That is exactly the blind spot a previous pass fell into (a missing isHost gate on a destructive action in the standings), and two of this round's findings (A11Y-1, UX-2) live in the same layer.

Cost is the honest caveat: bun test runs without a Vite transform, so component tests need a happy-dom preload and cannot use Vite-only features (import.meta.env, CSS imports) - as CLAUDE.md already spells out.

Recommendation: add a happy-dom preload plus Testing Library and cover the few highest-value cases: host vs. non-host affordances per screen, the buzz gate, and Room's state → screen mapping.

2. What is already strong

  • plus Connection lifecycle: host grace with a stable deadline ticker (no more second-by-second jump-back), a snapshot-carried countdown, a clean 1001 shutdown and reconnect with backoff+jitter, incl. an expiry test (-race green). The session lives in localStorage and survives closing the tab: re-entry as the same player (the host keeps its role within the grace window), an explicit "leave" is final.
  • plus Join anytime: you can join a running lobby in any phase. Mid-game joiners are Pending on the server, spectators with a fill-in overview, cleanly excluded from scoring/ranking/review/buzz (isRoundSpectator), and are activated automatically at the next round start. Covered by integration tests (pending status + activation).
  • plus Accessibility basics: a <main> landmark, live regions deliberately decoupled from the second ticker (the host-grace banner announces the situation once via role="alert" and hides the ticking digits), aria-pressed on the letter and flame toggles, keyboard operation throughout, toasts that pause on hover/focus. Inline field errors are linked via aria-describedby and announced as alerts, and every control sits at the natural tabindex="0" so Tab follows the visible order. The confirm dialog is the model implementation - focus on open, Tab trapped inside, Escape, and focus returned to the trigger (guarded against a trigger the dialog itself removed); A11Y-1 is about the QR popup never adopting it.
  • plus Frontend robustness: an ErrorBoundary (also around lazy chunks), a stackable 3D toast system with error/info variants, a join pre-check (checkLobby) with navigation locked during the check.
  • plus Tests: Go WS integration tests at the protocol level (-race green, ~15 s) and a frontend suite on the native bun test runner (26 tests) covering the client mirror of the engine rules (answerValidation, now including the non-ASCII casing and code-point-length cases) and parseServerEvent (Zod). Both run in CI. The Go harness is good enough that pinning the leave-then-reconnect scoring path took a single test function on the existing helpers.
  • plus Server-authoritative & end-to-end Zod validation of all incoming events (incl. host and checkLobby events).
  • plus Hardening: origin check via net.ParseIP (no glob a look-alike host could slip through), a per-connection token bucket, resource caps, the join backoff (which the checkLobby pre-check deliberately shares, so it cannot become an unthrottled enumeration oracle), a lobby reaper, CSP/HSTS-preload/COOP, immutable asset caching, hashed session IDs, no sessionId leak. The CSP script hash was recomputed from index.html this round and still matches main.go byte for byte. Lobby creation is the one path outside this net (SEC-1).
  • plus Render efficiency: all store accesses use fine-grained Zustand selectors (useStore(s => s.field)) instead of subscribing to the whole store, so components re-render only for the fields they read. Room hangs only on lobby?.state, for example, so the route tree no longer re-renders on every hostGrace second tick. Timer screens deliberately tick on local state, not on the store.
  • plus Consistency & CI: uniform sort idioms, TypeScript strict, Biome lint clean over src, a hard gofmt gate, go vet, bun test + WS integration tests in the pipeline, a multi-stage image that runs as a non-root user, and a Nix flake that pins the whole toolchain (Go 1.26, Bun 1.3) - the scan reproduced every gate through it. Formatting is the gap (CI-1).
  • plus Commentary that earns its keep: nearly every non-obvious decision carries its rationale (why the write happens after the unlock, why EmptySince is owned solely by the janitor, why the clipboard fallback exists). That is what made this scan able to separate deliberate choices from oversights - several things that look wrong at first glance turned out to be documented and correct.

3. Deliberately decided (no action needed)

The following points are chosen deliberately and documented in the README under "Deliberate decisions & known limitations". Each was re-checked against the code this round and still holds. They are not a problem for the intended use (LAN/party game) and are listed here so they are not re-raised as findings.

  • No host handoff: if the host does not return within 15 s, the lobby is closed, deliberately not transferring the host role.
  • Host "end round" is a fallback: a round normally ends through the first buzz or the timeout. The host button "end round" is deliberately de-emphasized (ghost) and only meant for the special case that no one can find anything else, it is not a standard flow.
  • A single global hub.mu: serializes all lobbies; at 500 players avg < 5 ms. Sharding is only needed with very many parallel games.
  • execCommand clipboard fallback: for plain-HTTP LAN, where navigator.clipboard is missing, deprecated but widely supported.
  • Player-list cache: evaluated and rejected, almost every broadcast follows a connected/score change that would invalidate a cache anyway.
  • No persistence layer: state lives in RAM; after a server restart clients are disconnected cleanly and return to the home screen.

4. Final project analysis

Overall verdict: production-ready for the intended use (real-time multiplayer party game on the LAN/browser). The game plays correctly end to end - a full protocol walkthrough against a running server confirmed every documented behaviour, including the awkward ones: mid-game joins landing as pending spectators, a kicked or departed player's replayed session being refused, the empty round skipping review, and returnToLobby zeroing every score. None of the ten open findings can change a game's outcome.

What is left is a consistent pattern rather than a set of unrelated slips: a good mechanism exists, and one place did not adopt it. Joining has a backoff, creating does not (SEC-1). The confirm dialog has focus management, the QR dialog does not (A11Y-1). The backend has a format gate, the frontend does not (CI-1). beginPlaying and endRound re-verify their state under the lock, beginCountdown does not (CONC-1). That is a cheap class of problem to close, because in each case the answer is already written somewhere else in this codebase.

Architecture & code quality

Clear separation: the Go backend as the single source of truth (engine, state machine, hub/handlers separated), the React SPA as a pure view layer. The state machine per lobby (Lobby -> Countdown -> Playing -> Reviewing -> RoundResult -> GameOver) is cleanly encapsulated; timers are idempotent via roundID+state, so late callbacks on aborted rounds fizzle out without effect. The code is commented throughout (every non-obvious decision with a rationale) and stylistically homogeneous.

Round participation used to be derived ad hoc in four separate places, each with a slightly different notion of Left, Pending and Connected - which is what let review and scoring disagree about who counted. It now goes through three named, documented predicates (isRoundSpectator / playsThisRound  / canPlayNextRound) that state why they differ, with the standings marked as the one deliberate exception. Every filtering path calls one of them, so that class of drift is closed off rather than patched on both sides.

Concurrency

A single global hub.mu serializes all lobby state; writes to the sockets happen after unlocking (coder/websocket serializes Conn.Write internally). Reconnect races are defused via identity guards (only the currently bound connection cleans up). go test ./... -race is green, incl. the end-to-end WebSocket tests. Client.sessionID - assigned across goroutines by closeLobby and handleKickPlayer, and previously the only field escaping the lock - is now written and read under hub.mu throughout, with the invariant recorded on the field itself.

Tests & CI

Backend: engine unit tests, benchmarks and protocol-level WS integration tests (among others a full round cycle, host-grace expiry, mid-game join -> pending -> activation). Frontend: the Zod parser and the engine-rule mirror, now on the native bun test runner - which also retired the zod-inlining workaround vite.config.ts needed under Vitest, so the build config is test-free again.

Remaining gap (TEST-1). There are still no render tests for the React components/screens; the UI is guarded by typecheck, lint and manual variant runs. Two of this round's findings (A11Y-1, UX-2) sit in exactly that layer, as did the missing isHost gate a previous pass had to catch by reading. The mirror suite, by contrast, covers the non-ASCII casing and code-point-length edges its invariant depends on.

Security

Server-authoritative with end-to-end input validation; a WS origin check against CSWSH (IP parsing instead of a glob), a per-connection rate limit, resource caps, a join backoff against code enumeration, an abandoned-lobby reaper. A strict CSP (script hash instead of unsafe-inline), HSTS/COOP/nosniff, hashed session IDs in logs, no sessionId leak to other clients. The CSP script hash was recomputed from index.html this round and still matches the value in main.go exactly. Appropriate for a game without accounts/persistence and without personal data.

Session invalidation is symmetric across every exit: leaving mid-game drops the session server-side just as a kick does, and a replayed id for a departed player is refused rather than relying on the frontend having cleared localStorage - confirmed live against the running server this round.

The one hole in that net is lobby creation (SEC-1): every other resource path is throttled or capped per connection, creation only by the global maxLobbies, so a single socket can walk the whole cap and deny lobby creation to everyone until the reaper catches up. Not a concern on a closed LAN; worth closing before any public deployment, which the project is otherwise already set up for.

UX & a11y

The host role is guided very well: inline field errors, confirmations on every destructive action, connection feedback, the commentator beamer view, QR/deep-link joining, "join anytime", and a start button that deliberately stays focusable while disabled so a click can shake the explanatory hint. The join flow is unusually careful - it seeds browser history so the back gesture walks the steps, pre-checks lobby availability before asking for a name, and discards stale replies.

The non-host view holds up too: destructive actions are only offered to whoever may perform them, and starting a round without a connected participant explains itself instead of doing nothing. A11y is solid on structure (landmark, aria-pressed toggles, the confirm dialog's full focus handling, the deliberate alert/ticker split in the host-grace banner) and on forms (errors linked and announced), with tab order following the visible order. Responsive, light/dark theme, and animations fully disabled under prefers-reduced-motion.

Where it slips is the second instance of a pattern: the QR modal never got the dialog behaviour (A11Y-1), and the live regions that appear with their content may not be announced at all (A11Y-2). On the UX side the walkthrough surfaced one real dead end - your own name stays reserved after you leave (UX-1) - and one screen that reports a two-second connection drop as "verlassen" (UX-2).

Optional next steps (non-blocking)

Not findings, just the idea worth keeping on file if the project is picked up again:

  • An optional persistence layer (e.g. Redis) if lobbies should ever survive a server restart; currently purely in-memory by design.

This report only documents, it reflects the current state without history. Nothing here blocks shipping: the app plays correctly end to end, and all ten findings are edge hardening, accessibility polish and documentation upkeep.
