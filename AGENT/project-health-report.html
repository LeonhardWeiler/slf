1. Open findings

No open findings. Every finding from the previous snapshot was implemented and removed here rather than ticked off - this report is a snapshot, not a history. All gates (gofmt, go vet, go test ./... -race, Biome, bun test, vite build) are green.

2. What is already strong

  • plus Connection lifecycle: host grace with a stable deadline ticker (no more second-by-second jump-back), a snapshot-carried countdown, a clean 1001 shutdown and reconnect with backoff+jitter, incl. an expiry test (-race green). The session lives in localStorage and survives closing the tab: re-entry as the same player (the host keeps its role within the grace window), an explicit "leave" is final.
  • plus Join anytime: you can join a running lobby in any phase. Mid-game joiners are Pending on the server, spectators with a fill-in overview, cleanly excluded from scoring/ranking/review/buzz (isRoundSpectator), and are activated automatically at the next round start. Covered by integration tests (pending status + activation).
  • plus Accessibility basics: a <main> landmark, live regions deliberately decoupled from the second ticker (the host-grace banner announces the situation once and hides the ticking digits), a focus trap plus Escape in the modal, aria-pressed on the letter and flame toggles, keyboard operation throughout, toasts that pause on hover/focus. Inline field errors are linked via aria-describedby and announced as alerts, the modal returns focus to whatever opened it, and every control sits at the natural tabindex="0" so Tab follows the visible order.
  • plus Frontend robustness: an ErrorBoundary (also around lazy chunks), a stackable 3D toast system with error/info variants, a join pre-check (checkLobby) with navigation locked during the check.
  • plus Tests: Go WS integration tests at the protocol level (-race green, ~15 s) and a frontend suite on the native bun test runner (26 tests) covering the client mirror of the engine rules (answerValidation, now including the non-ASCII casing and code-point-length cases) and parseServerEvent (Zod). Both run in CI. The Go harness is good enough that pinning the leave-then-reconnect scoring path took a single test function on the existing helpers.
  • plus Server-authoritative & end-to-end Zod validation of all incoming events (incl. host and checkLobby events).
  • plus Hardening: origin check, rate limit + caps + join backoff (also for the pre-check), a lobby reaper, CSP/HSTS-preload/COOP, immutable asset caching, hashed session IDs, no sessionId leak.
  • plus Render efficiency: all store accesses use fine-grained Zustand selectors (useStore(s => s.field)) instead of subscribing to the whole store, so components re-render only for the fields they read. Room hangs only on lobby?.state, for example, so the route tree no longer re-renders on every hostGrace second tick. Timer screens deliberately tick on local state, not on the store.
  • plus Consistency & CI: uniform sort idioms, TypeScript strict, Biome clean, a gofmt gate, bun test + WS integration tests in the pipeline, and a Nix flake that pins the whole toolchain.
  • plus Commentary that earns its keep: nearly every non-obvious decision carries its rationale (why the write happens after the unlock, why EmptySince is owned solely by the janitor, why the clipboard fallback exists). That is what made this scan able to separate deliberate choices from oversights - several things that look wrong at first glance turned out to be documented and correct.

3. Deliberately decided (no action needed)

The following points are chosen deliberately and documented in the README under "Deliberate decisions & known limitations". Each was re-checked against the code this round and still holds. They are not a problem for the intended use (LAN/party game) and are listed here so they are not re-raised as findings.

  • No host handoff: if the host does not return within 15 s, the lobby is closed, deliberately not transferring the host role.
  • Host "end round" is a fallback: a round normally ends through the first buzz or the timeout. The host button "end round" is deliberately de-emphasized (ghost) and only meant for the special case that no one can find anything else, it is not a standard flow.
  • A single global hub.mu: serializes all lobbies; at 500 players avg < 5 ms. Sharding is only needed with very many parallel games.
  • execCommand clipboard fallback: for plain-HTTP LAN, where navigator.clipboard is missing, deprecated but widely supported.
  • Player-list cache: evaluated and rejected, almost every broadcast follows a connected/score change that would invalidate a cache anyway.
  • No persistence layer: state lives in RAM; after a server restart clients are disconnected cleanly and return to the home screen.

4. Final project analysis

Overall verdict: production-ready for the intended use (real-time multiplayer party game on the LAN/browser). The architecture, hardening and test discipline were already good; the fix pass closed the one defect that could change a game's outcome, removed the structural seam that produced it, and tightened the edges around it. There are no known correctness, security or a11y defects left - the remaining limitations are all deliberate, documented design decisions (section 3).

Architecture & code quality

Clear separation: the Go backend as the single source of truth (engine, state machine, hub/handlers separated), the React SPA as a pure view layer. The state machine per lobby (Lobby -> Countdown -> Playing -> Reviewing -> RoundResult -> GameOver) is cleanly encapsulated; timers are idempotent via roundID+state, so late callbacks on aborted rounds fizzle out without effect. The code is commented throughout (every non-obvious decision with a rationale) and stylistically homogeneous.

Round participation used to be derived ad hoc in four separate places, each with a slightly different notion of Left, Pending and Connected - which is what let review and scoring disagree about who counted. It now goes through three named, documented predicates (isRoundSpectator / playsThisRound  / canPlayNextRound) that state why they differ, with the standings marked as the one deliberate exception. Every filtering path calls one of them, so that class of drift is closed off rather than patched on both sides.

Concurrency

A single global hub.mu serializes all lobby state; writes to the sockets happen after unlocking (coder/websocket serializes Conn.Write internally). Reconnect races are defused via identity guards (only the currently bound connection cleans up). go test ./... -race is green, incl. the end-to-end WebSocket tests. Client.sessionID - assigned across goroutines by closeLobby and handleKickPlayer, and previously the only field escaping the lock - is now written and read under hub.mu throughout, with the invariant recorded on the field itself.

Tests & CI

Backend: engine unit tests, benchmarks and protocol-level WS integration tests (among others a full round cycle, host-grace expiry, mid-game join -> pending -> activation). Frontend: the Zod parser and the engine-rule mirror, now on the native bun test runner - which also retired the zod-inlining workaround vite.config.ts needed under Vitest, so the build config is test-free again.

Remaining gap. There are still no render tests for the React components/screens; the UI is guarded by typecheck, lint and manual variant runs. That is what let a missing isHost gate survive in the standings, and it is the one area where a cheap safety net is still missing. The mirror suite, by contrast, now covers the non-ASCII casing and code-point-length edges that its invariant depends on.

Security

Server-authoritative with end-to-end input validation; a WS origin check against CSWSH (IP parsing instead of a glob), a per-connection rate limit, resource caps, a join backoff against code enumeration, an abandoned-lobby reaper. A strict CSP (script hash instead of unsafe-inline), HSTS/COOP/nosniff, hashed session IDs in logs, no sessionId leak to other clients. The CSP script hash was recomputed from index.html this round and still matches the value in main.go exactly. Appropriate for a game without accounts/persistence and without personal data.

Session invalidation is now symmetric across every exit: leaving mid-game drops the session server-side just as a kick does, and a replayed id for a departed player is refused rather than relying on the frontend having cleared localStorage.

UX & a11y

The host role is guided very well: inline field errors, confirmations on every destructive action, connection feedback, the commentator beamer view, QR/deep-link joining, "join anytime", and a start button that deliberately stays focusable while disabled so a click can shake the explanatory hint. The join flow is unusually careful - it seeds browser history so the back gesture walks the steps, pre-checks lobby availability before asking for a name, and discards stale replies.

The non-host view holds up now too: destructive actions are only offered to whoever may perform them, and starting a round without a connected participant explains itself instead of doing nothing. A11y is solid on structure (landmark, focus trap with focus return, deliberate live-region design, aria-pressed toggles) and on forms (errors linked and announced), with tab order following the visible order. Responsive, light/dark theme, and animations fully disabled under prefers-reduced-motion.

Optional next steps (non-blocking)

Nothing here is needed; these are the two ideas worth keeping on file if the project is picked up again:

  • Lightweight render/interaction tests for the core screens (e.g. Testing Library) as a complement to the logic tests. This is the one remaining blind spot - a missing host gate in the standings was invisible to typecheck, lint and the existing suite alike.
  • An optional persistence layer (e.g. Redis) if lobbies should ever survive a server restart; currently purely in-memory by design.

This report only documents, it reflects the current state without history. Nothing here is blocking; the app is in a good, shippable state and can be closed out as is.
