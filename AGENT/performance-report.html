Stadt Land Fluss - Performance Report

Frontend performance audit, produced alongside the UI/UX & bugfix pass (TODO items 1-17) · branch master

This report captures the frontend performance picture: measured bundle sizes from vite build, a static analysis of the render / re-render behaviour and the animation/transition budget, plus the concrete improvements made during this pass and a short list of non-blocking optimization ideas. Overall the app is lightweight and render-efficient; there are no performance regressions from the changes in this pass, and a few things got faster.

1. Bundle & loading

Production build output (gzip in parentheses). The start screen loads only the main chunk + CSS; the in-game view and the QR features are code-split and fetched on demand.

Chunk When loaded Raw Gzip
index (app core + Home) initial 401.7 kB 124.1 kB
index.css initial 42.3 kB 7.9 kB
Room (lobby + in-game screens) on entering a lobby 57.5 kB 16.9 kB
QrCode (generator) host reveals QR 23.8 kB 9.0 kB
QrScanner + worker user opens scanner 61.5 kB 16.8 kB

good Code-splitting already in place

Room (the whole lobby/game view), the QR generator and the QR scanner (with its sizeable worker) are lazy import()s. A first-time visitor on the start screen never downloads any in-game or camera code, keeping the initial paint lean. zod is deliberately inlined for the Bun test runtime but stays in the main chunk at runtime (it validates every server message, needed from the first connect).

Observation: the 124 kB gzip initial JS is dominated by React 19 + react-dom, TanStack Router, Zod v4 and Base UI - all core to the app. This is a reasonable budget for an interactive SPA; the biggest single lever would be trimming Zod or the router, neither of which is worth the complexity here.

2. Renders & re-renders

good Fine-grained store subscriptions

Every component reads Zustand through a narrow selector (useStore(s => s.field)); a repo-wide check found no bare store subscriptions. Notably Room only hangs on lobby?.state, so the per-second hostGrace countdown does not re-render the routed tree. useIsHost centralises the host lookup as a derived selector.

good Timers tick on local state

The countdown and stopwatch in GameScreen run on local useState intervals, not on the store, so a per-second tick updates just the digit and never cascades through the lobby state. Live regions are decoupled from the second ticker.

good Debounced answer sync

Keystrokes are batched into at most one answerUpdate per ~250 ms per category (with an immediate flush before a buzz and on unmount), instead of one message per keystroke - fewer renders on the commentator board and far less socket traffic.

good Player-list presence is change-driven

usePlayerPresence reacts only to added/removed player ids (for the fade-out), not to field updates or reorders, so live name/connection updates don't retrigger its effect.

3. Animations & transitions

The app uses short, one-shot CSS animations for feedback (fade, scale, pop, highlight) and cheap color/opacity transitions. During this pass the durations were trimmed so motion confirms an action without ever making the user wait on it (TODO item 11).

Effect Before After
animate-fade-in 0.25 s 0.15 s
animate-fade-out 0.20 s 0.12 s
animate-scale-in 0.18 s 0.12 s
animate-scale-out 0.16 s 0.10 s
animate-pop 0.30 s 0.20 s
animate-highlight 1.00 s 0.60 s
player-dot color transition 500 ms 200 ms
fill-progress bar width 300 ms 200 ms

The JS timeouts that gate the QR-popup close and the player-exit animation were matched to the new durations (120 ms and 140 ms). All animations are transform/opacity/color based (no layout-thrashing properties) and are fully disabled under prefers-reduced-motion: reduce.

4. Improvements implemented in this pass

  • Snappier motion: shortened the shared animation durations and two long transitions (see section 3), for a faster perceived response across the whole UI.
  • No banner flash on reload: the "no connection" banner is now deferred on the start screen and debounced (~1.2 s) elsewhere, so a fast (re)connect after a reload no longer flashes the banner and triggers a layout shift.
  • Less layout shift: constraining that banner to the button width keeps the start screen stable when it does appear.

5. Optimization ideas (non-blocking)

optional Preload the Room chunk

The lobby/game code is lazy-loaded when a player enters a lobby. On a slow link that shows a brief blank (Suspense fallback={null}). Preloading the Room chunk on hover/focus of the Create/Join buttons (a warm import()) would hide that latency without enlarging the initial bundle.

optional Keep lucide imports named

Icons are imported by name from lucide-react, which tree-shakes to only the used icons. Keep it that way (avoid import * as) so the icon cost stays proportional to what is actually rendered.

optional Defer Zod on the start screen

Zod sits in the initial chunk because it validates the first server messages. If the start screen ever needs to get even leaner, the schema module could be split so only the connect path pulls it in. Low priority - the current budget is fine.

Method: bundle numbers from vite build; render/animation findings from static analysis of the store selectors, effect dependencies and CSS. No runtime profiling harness is part of the repo; the app's scale (party-game lobbies) keeps per-frame work well within budget. Nothing here is blocking.
